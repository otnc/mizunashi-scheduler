# @mizunashi/core

取得パイプライン、状態判定、期間計算です。非公開パッケージ。

**プラットフォーム非依存です。** Web 標準 API のみを使い、`node:` の組み込みモジュールを import しません（ESLint で強制）。ストレージは `Storage` / `Cache` インターフェース越しに触るため、Cloudflare R2 / KV でもローカル FS でも差し替えられます。これが VPS 構成への移行可能性を担保しています。

## エントリポイント

| import | 内容 |
| --- | --- |
| `@mizunashi/core` | すべて |
| `@mizunashi/core/status` | 状態判定のみ（ブラウザ向け。parser を巻き込まない） |
| `@mizunashi/core/period` | 期間計算のみ |

## 取得パイプライン

```ts
await runIngest({ pageUrl, storage, cache, http }, new Date());
```

**状態を持ちません。** 前回何を取得したかを覚えず、起動のたびに「公式ページを見て、対象年のファイルを取ってきて、作り直す」だけを行います。

条件付き GET も鮮度判定も差分比較もしません。条件付き GET が節約するのは年 4MB 程度で、リクエスト数は減りません。4 種類の状態を管理する複雑さに見合いませんでした。

**副産物として自己修復します。** パーサやバリデータを修正してデプロイすれば、次の実行で派生データが自動的に作り直されます。手動の復旧手順が要りません。

### 保存の方針

| 対象 | ポリシー |
| --- | --- |
| `raw/`（原本） | **無期限保存・削除禁止**。公式サイトから消えたら、これが唯一残る版になる |
| `derived/`（派生データ） | 今年と来年のみ。それ以外は日次で破棄（原本から再生成できるので可逆） |

`Storage.delete` は `raw/` 配下に対して `ImmutablePrefixError` を投げます。原本の削除は復元不能なので、ESLint ルール・インターフェース・各実装の三重で止めています。

原本のキーは内容ハッシュ由来（`raw/objects/{sha256}.xlsx`）です。2 週間ごとに無条件取得するため、キーが内容から決まっていれば自然に重複排除されます。**キーに年を含めないのは、保存がパースより先に行われ、その時点では対象年が確定していないため**です（`R2.xlsx` の中身が 2021 年だった前例があります）。

## 状態判定

```ts
import { CalendarView, computeStatus } from '@mizunashi/core/status';

const status = computeStatus(now, new CalendarView(years));
```

**セッションを平坦な時系列リストにして二分探索します。** 「日 → セッション」の二重ループは境界処理を間違えやすく、1 日 1 回と 3 回でコードパスが変わります。平坦化すれば回数に依存しません。

返り値で特に重要なのは次の 2 つです。

| フィールド | 意味 |
| --- | --- |
| `nextToday` | 今日この後の次。**日をまたがない** |
| `next` | 次。日をまたいで探す |

両者の差が「今日まだ入れるか」を表します。現地へ向かうかの判断が真逆になるため、単一の「次はいつ」では表現できません。

「本日終了」と「初回前」は `remainingCountToday` では区別できないので、`endedCountToday` を併せて見てください。

## 時刻の扱い

**すべて JST 固定です。** Cloudflare Workers は UTC で動くため、ローカル時刻依存の `Date` メソッドは `status/jst.ts` の外では使いません（ESLint で禁止）。日本にサマータイムがないので固定オフセットで安全です。

`activeYears()` は必ず JST の年に基づきます。UTC で判定すると 12/31 の日本時間 9 時以降でずれます。
